From a rough brief to a finished design in Figma

8 phases · 17 steps · a gate after every phase. Claude follows this map exactly. Open it any time to see where you are.

Core rules

  • AI is the engine, you are the director. Claude works fast; you approve every phase.
  • Think before you draw. Steps 01–06 decide most of the final quality.
  • Test the style small first. 5 proof screens before the full UI.
  • One source of truth at a time: proof screens → baseline tokens; final UI → Primitive and Semantic tokens; real Figma components → Component variables.
  • No guessing. Anything not in the brief is written as an ASSUMPTION.
  • Only assets you may use: the client's own files, or open-source fonts and icons that allow commercial use.

Phase 1

Brief

Cowork · Product Manager / Business Analyst

Turn a rough request into clear requirements. Check every input and lock the platform before any research.

01Intake & input check

Read everything the user provided and make sure nothing is missing before work starts.
Do
  • Read 01-brief/ and all of 02-assets/ (logo, moodboard, icons, fonts).
  • Show the input checklist as a table: ✅ found / ⚠ missing.
  • Brief missing → STOP and say exactly what to add.
  • Logo, moodboard, icons or font missing → clear ⚠ WARNING with what to add, where, and 1–2 options (e.g. icon-library.txt → Lucide; font-name.txt → Inter).
  • Flag license risks: fonts that can't be redistributed, icons copied from other apps or paid packs, a logo that is only a screenshot.
  • Echo back 3–5 lines (name · industry · platform · brand color · one-line read) plus the plugin slug, and ask to start.
  • After yes: rename both plugins with the project slug (folders, manifest name and ID, UI headings, plugin-data namespaces, Figma labels) — names only.
Output
03-research/01-intake.md · 06-figma-plugins/<slug>-importoken · <slug>-foundation-style
Check
  • Every required input is ✅, or has a warning the user has seen.
  • Nothing is invented.
  • The user confirmed the echo-back.
  • phongdesigns left inside the plugin folders = 0 (counted).

08Moodboard & screen references

Lock the style AND find real screens with the right content and layout, so the AI builds each screen accurately.
Do
  • Describe the general moodboard in words: color use, type, corner radius, density, shadows, imagery.
  • Pick the key screens (at least the 5 proof screens) from the sitemap.
  • For each key screen, give 3 SHORT search keywords, 2–3 words each — domain + screen or a UI pattern, no style words (e.g. 'car rental', 'date picker', 'QR ticket'). Long phrases find almost nothing.
  • Say where to search: Mobbin (filter by category + screen pattern), Dribbble, Behance, Pinterest, Page Flows.
  • STOP and wait: the user saves 1–3 references per screen into 02-assets/moodboard/screens/S##-name/.
  • Read the references: note the layout pattern of each screen (sections, order, main components) and check they match the style.
  • Lock icons (client set or the ONE library in icon-library.txt) and the font. Mark every asset static or runtime.
Output
03-research/08-moodboard.md (style + keyword table + layout notes per screen) · 02-assets/moodboard/screens/
Check
  • Style described in words.
  • Every key screen has keywords AND 1–3 references with the right content/layout.
  • Icon source and font locked.
Prompt

09Five proof screens

Test the style on 5 key screens before building the whole product.
Do
  • Pick 5 screens that show different things (e.g. home, list, detail, form, success).
  • Build them in ONE HTML file with the chosen palette, moodboard, icons and font — follow the screen references from Step 08 for content and layout.
  • CSS variables in :root, clean semantic class names, no inline styles.
  • Review; if the style is off, go back: update Step 07 (palette) or Step 08 (moodboard style), mark it done (updated) in _progress.md, then regenerate the proof screens. This 08 ↔ 09 loop is normal — repeat until the style is right.

Final UI

Claude Design (build) + Cowork (review)

Build every screen in Claude Design, then make the final UI the single source of truth.

12Master spec → image prompts → Claude Design → final UI

Build all screens in one pass from one complete spec.
Do
  • Write master-spec.md: brief, research, sitemap, user flows, palette, moodboard, tokens — every screen with every state.
  • List every image slot (IMG01, IMG02…) with size and ratio, and write image-prompts.md: one prompt per slot in the approved look and palette.
  • WAIT: the user generates the images (e.g. ChatGPT) and saves them in 02-assets/images/ with the given file names.
  • Write claude-design-prompt.md: stick to the proof style and tokens, clean classes, :root variables, use the images in their slots.
  • In Claude Design: attach the spec, the prompt, the logo, the proof HTML and the images; answer its questions; build.
  • Export ONE HTML file.

15Figma MCP: components, swap & token matching

Build real components and link everything to the tokens.
Do
  • Paste the Figma link into Cowork.
  • First an inventory of components and a batch plan — wait for approval. Then 3–5 components per turn, small parts first, each checked before the next.
  • Read the approved screens and master spec, then build the real components directly in Figma with all required states, variants and names.
  • For each component, compare its reusable properties with the Component collection; proactively create any missing Component variables, alias them to Semantic variables, bind them, and mirror the additions to 05-tokens/3-component.json.
  • Swap instances into the screens — only UI chrome (buttons, tabs, inputs), never cards with real content.
  • Match every color, font, radius and shadow to the variables via MCP; list anything that doesn't match.
  • Screenshot review after each group.
Output

Check

  • Every reusable component decision has a bound Component variable and a matching entry in 3-component.json.
  • No real content lost.
  • No hard-coded values left.

Appendix

Figma MCP gotchas

ProblemFix
resize() on an auto-layout frame sticks at 10px height.Use AUTO (hug) on the axis that should shrink; don't resize that axis.
Section children are positioned relative to the section.Set the section geometry first, then the children.
Prototype fails: target is not top-level.Move screens to top level before wiring.
Swapping a card with real content loses the data.Swap only chrome (buttons, tabs, inputs); screenshot-review each group.
One Bottom Tab Bar lights the same tab on every screen.Make a variant set with an Active axis.
A grey input is mistaken for a disabled button.Use a strict match: color + size + text + position.
The font silently falls back to another font.Install the project font in Figma before creating styles.
An icon loses its colour when swapped to another icon.Flatten every icon component to one vector layer named Vector (Step 14). Never re-set a swap to the same icon — it resets the colour.
Block buttons shrink to hug width after a swap.Set them back to Fill; compare widths with the Screens Backup page.
Single-line text wraps after a text style is applied.Set the text layer to auto width.
A bottom sheet shows a grey line at the bottom.It floats 1–3 px above the frame — close the gap to 0.
Figma refuses a second prototype starting point.Two flows start on the same frame — start the second flow on its first different screen.
Claude can’t mark screens “Ready for dev”.Not possible through MCP — select the frames in Dev Mode and mark them yourself.
All variants of a component show the same label.Re-set each variant's own text after building the set.
Something broke during swap and you can't tell how it looked.Keep an untouched Screens Backup page (made in Step 14) and compare.
The UI comes out flat.Stick to the proof screens and the moodboard; be specific about shadows, radius, hierarchy.
